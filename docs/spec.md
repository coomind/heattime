# 폭염 경기운영 의사결정 시스템 — GPT 작업용 패키지

> 가칭: **히트타임(HeatTime)** — 이름은 자유롭게 바꿔도 됨
> 목적: 2026 경기스포츠산업 공모전 출품용 시연 가능한 웹 서비스 제작
> 마감: **2026-10-30(금) 18:00** 온라인 접수 / 1차 발표 11-13 / 2차 발표심사 11-20
> 제출물: 시연 포함 7분 발표자료 + 서비스 링크·활용 영상 등

이 문서는 다섯 부분으로 구성된다.

1. 아이디어 요약과 포지셔닝
2. 기능 명세서(요구사항·데이터 모델·알고리즘·화면)
3. 참고 자료와 근거(출처 링크)
4. GPT에 넣을 프롬프트(마스터 프롬프트 + 단계별 프롬프트)
5. 일정, 발표 구성, 예상 질의응답

## 1. 아이디어 요약

### 한 줄 정의
대회 주최자가 대진표와 구장 정보를 입력하면, 기상청 예보와 구장 조건으로 **경기별 열 스트레스(WBGT)를 예측**하고, 위험도에 따라 **쿨링브레이크 삽입·경기시간 단축·킥오프 재배치**를 자동 권고하며, **참가팀 알림과 운영 판단 기록**까지 남기는 웹 서비스.

### 공모전 분야
- 1순위: **안전·시설 관리 기술** (경기장 안전관리, 응급상황 대응)
- 2순위 연결: **대회 운영·관리 기술** (스마트 시스템, 선수 관리, 안전 시스템)

### 해결하는 문제
- 여름철 생활체육·유소년 대회는 한낮 경기 진행 여부를 운영자 감에 의존한다.
- 지자체 대응은 "무더위 시간 운동 자제" 현수막 수준에 머무는 사례가 있다(진도군, 2026년 7월).
- 해외는 WBGT 기반 경기 운영이 규정화되는 추세다(텍사스 고교체육연맹 UIL, 2026–27 학년도부터 의무).
- 국내 산업현장에는 WBGT·체감온도 IoT 관리 솔루션이 있지만(케이웨더, 롯데건설·엔비즈소프트), **경기 일정·연령별 기준·쿨링브레이크 같은 스포츠 운영 기능은 없다.**

### 포지셔닝 원칙
- 우리는 **센서 회사가 아니다.** 기상청 데이터와 (선택) 형식승인 WBGT 측정기를 연동하는 **스포츠 운영 소프트웨어**다. → 케이웨더 같은 업체는 경쟁자가 아니라 잠재 파트너.
- 우리는 **의료기기가 아니다.** 공개된 스포츠 단체 가이드라인을 운영 규칙으로 바꿔 주는 의사결정 보조 도구이며, 최종 판단은 주최자가 한다.
- 추정값의 불확실성을 숨기지 않는다. 범위로 보여준다. 판정은 구장 보정을 더한 중앙 추정으로 한다(2026-10-21 변경, 아래 (D) 참고).

### 기술적 차별점(심사에서 "계산기 아니냐"는 질문에 대한 답)
1. **기상 예보 → 경기장 단위 WBGT 추정 엔진**: 기상청 예보에는 일사량이 없으므로 태양고도와 하늘상태로 일사량을 추정한 뒤 WBGT 물리 모델에 넣는다.
2. **현장 보정 구조**: 관측소 기반 추정치는 실제 경기장보다 낮게 나오는 경향이 연구로 보고됨 → 구장별 보정값(offset)과 현장 실측 입력으로 보정.
3. **제약 최적화 기반 일정 재편성**: 구장 수, 팀별 최소 휴식, 토너먼트 선후관계, 연령별 위험 기준을 동시에 만족하면서 열 노출과 일정 변경을 최소화(OR-Tools CP-SAT).
4. **불확실성 기반 판정**: 점추정이 아니라 범위로 판정하고, 대상 연령에 따라 보수성 조절.

## 2. 기능 명세서

### 2.1 사용자
| 사용자 | 하는 일 |
|---|---|
| 대회 운영자(체육회·협회·학교 운동부 담당) | 대회·구장·대진 입력, 위험도 확인, 재편성안 승인, 알림 발송, 기록 출력 |
| 참가팀 지도자 | 알림 수신, 변경된 일정·쿨링브레이크 확인(읽기 전용 링크) |
| 현장 요원(선택) | 대회 당일 실측 WBGT 값 입력 |

### 2.2 MVP 범위 (10/30까지 반드시)
- [M1] 구장 등록: 이름, 위경도, 표면(인조잔디/천연잔디/흙/실내), 그늘 여부, 보정값
- [M2] 대회 등록: 종목(축구 우선), 연령 그룹, 정책(가이드라인) 선택
- [M3] 대진 입력: CSV 업로드 또는 간단 폼 (경기 ID, 라운드, 팀A, 팀B, 구장, 시작시각, 경기시간, 선행 경기)
- [M4] 기상 데이터 수집: 기상청 단기예보(미래) / ASOS 시간자료(과거 재현용)
- [M5] WBGT 추정 + 불확실성 범위 + 위험 단계 산정 (구장 × 시간)
- [M6] 위험도 히트맵: 가로 시간, 세로 구장, 셀 색 = 단계, 위에 경기 블록 오버레이
- [M7] 경기별 권고: 정상 / 쿨링브레이크 추가 / 경기시간 단축 / 시간 이동 / 연기
- [M8] 자동 재편성: 원래 일정 vs 재편성안 비교 화면, 운영자 승인 버튼
- [M9] 알림: 시연용 모의 발송(발송 로그 화면). 실제 문자·카카오 연동은 확장 항목
- [M10] 운영 기록: 판단 근거(입력 데이터, 산정값, 적용 기준, 운영자 조치)를 PDF/CSV로 출력
- [M11] **재현 모드(Replay)**: 과거 날짜를 고르면 그날 실제 관측 기상으로 시뮬레이션 → 발표 시연 핵심

### 2.3 확장 범위 (발표에서는 로드맵으로만)
- 현장 WBGT 측정기 연동(형식승인 장비 API 또는 수동 입력)
- 카카오 알림톡·SMS 실제 발송
- 미세먼지·한파·낙뢰까지 포함한 전천후 경기운영
- 응급 대응 모듈(가까운 AED 위치, 응급 프로토콜 체크리스트)
- 영상 기반 개인 부하 측정(P2B 파이프라인) — **현재 연구 단계, 아마추어 영상 품질 미통과. 기능으로 주장하지 않음**

### 2.4 데이터 모델 (초안)

### 2.5 알고리즘 명세

#### (A) 기상 입력
- 미래(실사용): 기상청 **단기예보** 계열 API — 1시간 단위 기온(TMP), 습도(REH), 풍속(WSD), 하늘상태(SKY), 강수형태(PTY).
- 과거(재현 시연): 기상청 **ASOS 시간자료** — 기온, 습도, 풍속, (지점에 따라) 일사량.
- 격자 변환: 기상청이 공개한 위경도↔격자(Lambert Conformal Conic) 변환식 사용.
- ⚠️ 정확한 API 엔드포인트명, 파라미터, 응답 필드명, 일사량 제공 지점은 **공공데이터포털/기상청 API허브 문서로 직접 확인**할 것. 추측으로 작성 금지.

#### (B) 일사량 추정 (예보에는 일사량이 없음)
1. 위경도·시각으로 태양 천정각 계산 (pvlib.solarposition 등)
2. 맑은 하늘 일사량(GHI_clear) 계산 (pvlib.clearsky 등)
3. 하늘상태로 운량 추정 → 구름 보정
   - SKY 1 맑음(운량 0–5/10) → 대표값 0.25
   - SKY 3 구름많음(6–8/10) → 0.7
   - SKY 4 흐림(9–10/10) → 0.95
   - Kasten–Czeplak 형태: `GHI = GHI_clear × (1 − 0.75 × c^3.4)` (c = 운량 비율)
4. 강수(PTY ≠ 0)면 일사량을 추가 감쇠(설정값)
5. 재현 모드에서 관측 일사량이 있으면 관측값을 우선 사용하고, 추정값과 비교 그래프를 남긴다(엔진 검증 근거로 발표에 사용).

#### (C) WBGT 추정
- 정의(실외): `WBGT = 0.7·Tnw + 0.2·Tg + 0.1·Ta`
- 1순위 방법: **Liljegren 모델**(Liljegren et al., 2008) — 기온·습도·풍속·일사·기압으로 자연습구온도(Tnw)와 흑구온도(Tg)를 물리적으로 계산. 미국 기상청 WBGT 예보에도 쓰이는 계열의 방법.
  - 구현 후보: 공개 구현(예: PyWBGT 등 Liljegren 포팅)을 찾아 **라이선스·설치 가능 여부 확인 후** 사용, 불가하면 논문 기반으로 직접 포팅.
- 2순위(폴백): 간이식(그늘 기준 근사식 + 일사 보정). 폴백 사용 시 화면과 기록에 "간이 추정"으로 표시.
- 풍속 보정: 기상관측 풍속(10m)을 사람 높이(약 2m)로 보정하는 로그/멱법칙 적용(계수는 설정값).
- 경기장 보정: `wbgt_field = wbgt_est + field_offset_c`
  - 근거: 미국 연구에서 경기장 실측 WBGT가 지역 관측소 기반 추정보다 평균 약 2.4–2.5℃ 높았음.
  - 같은 연구와 캔자스대 백서에서는 **표면 종류(인조잔디 vs 천연잔디) 간 WBGT 차이는 크지 않았다** → 표면별 추가 보정은 기본 0, 설정으로만 허용. (인조잔디는 표면온도·기온이 높다는 별도 근거가 있으므로 "화상·표면온도 주의" 안내는 따로 표시)
- 불확실성 범위: 기본 ±1.5℃(설정값). 현장 실측이 들어오면 그 시점 이후 오차를 실측 기반으로 갱신.
  - 근거: 스마트폰 앱 추정 WBGT가 현장 실측과 체계적으로 어긋난 연구들이 있음(과대/과소 모두 보고).

#### (D) 위험 단계와 정책
기본 정책 2종을 내장하고 운영자가 선택하게 한다. **수치는 반드시 원문 출처와 대조해 확인 후 입력.**

정책 1 — 일반 운동(일본 스포츠협회 계열 지침, 한국과 기후가 비슷한 기준)
| 단계 | WBGT(℃) | 의미 | 기본 조치 |
|---|---|---|---|
| 0 통상 운영 (원 지침 표기: 거의 안전) | < 21 | 일반 활동 | 수분 보충 안내 |
| 1 주의 | 21–25 | 위험 증가 | 정기 수분 보충 |
| 2 경계 | 25–28 | 열사병 위험 | 적극적 휴식 → **쿨링브레이크** |
| 3 엄중경계 | 28–31 | 위험 높음 | 격렬한 운동 피함 → **경기시간 단축/시간 이동** |
| 4 운동 중지 | ≥ 31 | 원칙적 중지 | **연기/취소** |

> 2026-10-11 변경: 0단계 화면 표시명을 "거의 안전"에서 "통상 운영"으로 바꾼다. 안전을 판정·보장하는 문구로 읽히지 않게 하기 위한 명세 작성자 승인 변경이며, 원 지침 단계명은 근거 화면·PDF·정책 설정에 출처와 함께 남긴다.

정책 2 — 축구 경기(FIFPRO 권고 반영)
- WBGT 26℃ 초과: 냉각 조치(쿨링브레이크) 필수
- WBGT 28℃ 초과: 경기 연기 권고

판정값(설계 가정 — **전문가 자문 필요 항목으로 표기**)
- 2026-10-21 작성자 결정((나) 조건): 모든 연령에서 `wbgt_c`(관측 기반 추정 + 구장 보정 2.5℃의 중앙 추정)를 판정에 쓴다. 범위(`wbgt_low_c`~`wbgt_high_c`)는 화면과 기록에 계속 표시하지만 판정에 쓰지 않는다. 설정: `backend/config/policies.yaml`의 `age.upper_bound_groups: []`.
- 이전 기준(2026-10-20까지): 유소년(U15 이하)·시니어는 `wbgt_high_c`(상단값) 사용 + 한 단계 상향 옵션, 성인은 `wbgt_c`. 한 단계 상향 옵션은 상단 판정 연령에만 적용되므로 지금 기준에서는 쓰이지 않는다.
- 단계 경계, 구장 보정 2.5℃, 범위 계산(±1.5℃), 최적화 목표와 제약은 바꾸지 않았다.

#### (E) 경기별 권고 로직
경기 시간 구간 [start, end] 동안 구장의 시간별 위험 단계 중 **최대값**으로 판정.
- 단계 2: 각 하프 중간에 쿨링브레이크(기본 3분, 설정 가능) 삽입 → 종료 시각 재계산
- 단계 3: 하프 시간 단축(설정 비율) **또는** 위험이 낮은 시간대로 이동 제안
- 단계 4: 해당 시간대 배정 금지 → 이동 또는 연기

#### (F) 일정 재편성(제약 최적화)
- 도구: Google OR-Tools CP-SAT
- 결정변수: 각 경기의 (구장, 시작 슬롯) — 슬롯 단위 10분 또는 15분
- 하드 제약
  - 같은 구장·같은 시간 중복 금지(경기시간 + 정리 시간 포함)
  - 같은 팀의 연속 경기 사이 최소 휴식(연령별 설정값)
  - 선행 경기(depends_on) 종료 후에만 시작
  - 판정 단계가 "중지"인 슬롯 배정 금지
  - 운영 가능 시간(예: 07:00–20:00), 조명 없는 구장은 일몰 전
  - 대회 일자 범위 내
- 목적함수(가중합, 가중치 설정 가능)
  - Σ 경기별 열 노출 점수 (단계 가중 또는 WBGT 초과분 적분)
  - \+ Σ 원래 일정과의 시간 차이(분)
  - \+ 구장 변경 횟수 × 페널티
- 해가 없으면: 연기가 필요한 경기 목록과 그 이유를 출력
- 시간 제한: 10초 내 최선해, 그래도 없으면 탐욕적 폴백(위험 낮은 빈 슬롯 순서대로 배정)

### 2.6 화면 구성
1. **대시보드**: 오늘/선택 날짜, 구장×시간 위험도 히트맵, 경기 블록 오버레이, 단계별 경기 수 요약
2. **경기 상세**: 시간별 WBGT 그래프(범위 음영), 적용 기준, 권고 조치, 근거 데이터
3. **재편성 비교**: 원래 vs 제안(간트 차트 2개 나란히), 변경 사유, 승인/수정/거절 버튼
4. **알림 로그**: 팀별 발송 내용(모의), 발송 시각
5. **운영 기록**: 판단 이력 테이블, PDF/CSV 내보내기
6. **재현 모드**: 날짜·지역 선택 → "그날 이 대회였다면" 시뮬레이션 실행
7. **설정**: 정책 선택, 연령 보정, 쿨링브레이크 길이, 보정값, 불확실성 범위

디자인: 모바일 대응(현장 운영자는 휴대폰으로 봄), 큰 글씨, 단계 색상은 색맹 고려(색 + 아이콘 + 텍스트 병기).

### 2.7 기술 스택(권장)
- 백엔드: Python 3.11+, FastAPI, SQLite(시연) → PostgreSQL(확장), OR-Tools, pvlib, pandas
- 프론트엔드: React(Next.js 또는 Vite) + 차트 라이브러리(Recharts/ECharts) + 간트 차트

- 테스트: pytest (WBGT 엔진, 격자 변환, 스케줄러 제약 검증)

### 5.3 예상 질의응답
1. **앱 추정 WBGT는 부정확하다는 연구가 있는데?** → 그래서 범위로 함께 보여주고, 판정에 쓴 값(구장 보정을 더한 중앙 추정)과 범위 상단으로 판정했을 때의 단계를 근거 화면에 나란히 적는다. 예보는 전날 계획용, 당일은 현장 측정기 값으로 보정하는 2단 구조다.
2. **케이웨더 같은 회사가 하면 되지 않나?** → 그들은 센서와 산업안전 대응에 강하다. 우리는 경기 일정·연령 기준·쿨링브레이크라는 스포츠 운영 로직이다. 측정기 연동 파트너로 본다.
3. **여름 한철 아닌가?** → 같은 엔진으로 미세먼지·한파·낙뢰까지 확장한다.
4. **기준 수치는 누가 정했나?** → 공개된 스포츠 단체 지침을 그대로 쓰고 출처를 기록에 남긴다. 연령 보정은 전문가 자문이 필요한 항목으로 명시했다.
5. **사고 나면 책임은?** → 최종 결정은 주최자. 시스템은 근거 기록을 남겨 판단 과정을 투명하게 만든다.
6. **실제로 써본 곳이 있나?** → 현재는 재현 시뮬레이션 단계. (인터뷰한 곳이 있으면 그 반응을 사실대로)
7. **왜 경기도인가?** → (경기도 내 구장으로 시연한 점, 도 단위 생활체육 대회 규모를 근거로. 수치는 확인한 것만 사용)
